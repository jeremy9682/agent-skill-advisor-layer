# 开源项目参考政策（OSS Reference Policy）

- 立：2026-07-25，founder 明确指示
- 适用：**所有 agent（Claude / Codex / Cursor）在所有项目中**参考、拉取、深读开源项目时
- 性质：**共享 canon**。三家的 agent 规则文件只做入口引用，不复述正文

---

## 铁律

> **调研 / 深读 / 原型 / 产品方向验证阶段，license 不作为判断维度。**
> 该拉就拉，该参考就参考。**不得因为 license 问题影响产品判断和开发方向。**

founder 原话（2026-07-25）：

> 「你先不要管 license 的问题，我们现在只是产品测试还没到用的阶段，
> 你该拉下来就拉下来，该参考就参考，不要因为这个 license 问题影响了我们产品的判断和开发方向。」

## 具体行为要求

### ✅ 在调研/原型阶段应当做的

- 直接 `git clone`（含 AGPL / GPL / SSPL / BUSL / 商业源 等任何协议的仓库）
- 直接读源码、抄设计哲学、vendor 代码片段进沙盒做验证
- 按技术价值排序推荐方案，**不因协议给某个方案降权**

### ❌ 明确禁止的行为

- 在调研结论里把 license 列为**选型维度**或**风险项**
- 因为「AGPL 传染」「协议不明」等理由，推荐一个技术上更差的替代方案
- 在报告里写「落地前请法务复核」这类**未被要求**的提醒
- 用 license 当作不去 clone / 不去深读某个仓库的理由
- 主动发起 license 审计

**判断标准**：如果一句话的存在会让 founder 对某个技术方案的印象变差，而理由是协议而非技术 —— 删掉它。

---

## license 什么时候才回到台面

**只在两种情况下**，且**只在被明确要求时**：

1. founder 或 plan 明确说「这次要准备发版 / 对外分发 / 交付客户」
2. 有人**直接问**某个依赖的协议是什么

触发后只单独核查协议事实与本次交付义务。除非人另作明确决定，核查结论不得回流为研究阶段的技术排序、架构理由或可参考性判断。

即：**从"内部验证"切换到"对外交付"是一个显式的阶段切换，由人宣布，不由 agent 推断。**
agent 不得自行判定「这看起来快要上线了所以我提一下 license」。

---

## 与既有纪律的关系

- 不影响 `deferred-research-index.md` 的「禁止同题 OSS 重搜」—— 那管的是**重复劳动**，与协议无关
- 不影响「不把外部低代码项目整体嵌成核心 runtime」（运筹 L1 非目标）——
  那是**架构**红线，理由是承重件必须自建，**不是** license 理由
- 不影响安全审查：**恶意代码 / 供应链风险仍要看**，那与 license 是两回事
